## D-2026-09-17-01 · Выгрузка БД на сервер падает с WinError 2 (WAL-сайдкары) — В планировании

**Проблема (подтверждена логами 2026-09-17 09:47–10:45, admin):**
`[ERROR] [sync] Ошибка выгрузки БД на сервер: [... graph_rag.db-shm / graph_rag.db-wal ... WinError 2]`.
Блок выгрузки у админа (`sync_*` поток, ~строки 2474–2486) делает `shutil.rmtree(server_db)` → `shutil.copytree(local_db, server_db)`. Паук Graph RAG (`App._graph_spider_loop`, ~4449) держит открытое sqlite-соединение с `graph_rag.db` весь раунд; SQLite в WAL-режиме удаляет сайдкары `-shm/-wal` при закрытии/checkpoint → `copytree` пытается скопировать исчезнувший файл → `shutil.Error`. Дополнительные риски: (а) `rmtree` выполняется ПЕРВЫМ — любой сбой копирования оставляет сервер без базы; (б) `clear_system_cache()` не закрывает соединения паука (кэш клиента на `self._graph_chroma_client`) — `chroma.sqlite3` копируется «живым»; (в) `.db` может скопироваться без `-wal` → потеря последних записей.

**Принятое направление решения:**
`ignore_patterns("*.db-shm", "*.db-wal")` + консистентный снапшот `graph_rag.db` через `sqlite3.backup()`; пауза паука на время выгрузки (флаг `_db_syncing` уже есть, но раунд, стартовавший до флага, может выполняться — требуется гарантия тишины писателя); рассмотреть «копия во временную папку → атомарная замена» вместо `rmtree`-в-начале. Финальная схема — у архитектора (задание передано 2026-09-17, отдельно проверяется поведение `shutil.copytree`: агрегация ошибок vs прерывание).

**Затронутые функции:** блок выгрузки в `sync_*` (~2474–2486), `_graph_spider_loop` (~4449, координация паузы).

**Верификация (план):** вручную воспроизвести (держать открытым sqlite-соединение во время выгрузки); после фикса — ERROR-строки в логе отсутствуют; диагностика шаг 6 (`integrity_check` ~7735) на серверной копии OK.

## D-2026-09-17-02 · GraphRAG grounding: протухшие якоря рёбер; автолечение в 2 уровня — В планировании

**Проблема (подтверждена логами 2026-09-17, многократно):**
`[WARNING] [graph] GraphRAG grounding: N чанков-источников не найдено в smk_docs (файл пере-чанкован ...?) — рёбра выданы без фрагмента`.
Chroma `smk_docs` хранит чанки с id `{file_path}_chunk_{N}`; `graph_rag.db.relations` хранит рёбра-триплеты со ссылками `chunk_id`/`source_chunk`. При пере-чанковании файла id сместились; self-heal при sync (~2389–2402) чистит по префиксу только файлы, изменённые в текущей синхронизации — легаси-рёбра (в т.ч. с NULL `source_chunk`, колонка добавлена миграцией ~578–592) остались. `_ground_graph_rows` (~2803–2912) не находит чанки (строка WARNING ~2839) → рёбра выдаются level="none", без цитаты-доказательства. Данные НЕ потеряны; деградация — отсутствие подтверждения. Замечание: часть warningов может порождаться «методом Б» (окно `_rebuild_window_chunk_ids` из протухшего `chunk_id`), а не только NULL-якорями.

**Принятое решение (подход):**
Фоновое автолечение внутри цикла паука (только админ, пауза при `_db_syncing`, раз в N раундов):
- **Уровень 1 (0 токенов LLM):** SQL находит рёбра с невалидными ссылками; для каждого затронутого файла одним batch-get достаются ТЕКУЩИЕ чанки из `smk_docs` (префикс id / `where={"file_path": fp}`), ребро пере-якорится substring-матчером `_match_triplet_to_chunk` (~2743, без LLM) → UPDATE `relations`. Открытый вопрос для архитектора: обновлять ли только `source_chunk` или оба поля (`chunk_id` + `source_chunk`) — grounding восстанавливает окно ИЗ `chunk_id`, протухший `chunk_id` сам порождает warningи.
- **Уровень 2 (тратит токены):** файл, где матч не сошёлся → DELETE `relations` + `processed_chunks` по префиксу → паук в обычном цикле (кандидаты = all_ids − processed_chunks, ~4524) пере-извлекает штатным FIFO/poison-guard.
- Лимиты: ≤ K файлов за проход (настройка), т.к. в продакшене наблюдались 429 rate-limit OpenRouter; переключатель в `DEFAULT_SETTINGS` (`graph_rag_*`, ~4033) и в UI-вкладке графа (~6833–6891, сохранение ~7407–7433). GraphML-«scheme»-рёбра (id без `_chunk_{N}`) — не лечить, пропускать.
- Запись не параллелить с раундом паука (сериализованный писатель ~4616+); не ломать `fail_counts`/poison-guard.

**Затронутые функции:** `_ground_graph_rows` (детектор, только чтение — не триггерить лечение из query-пути!), `_match_triplet_to_chunk`, `_graph_spider_loop`, `init_graph_db`, `DEFAULT_SETTINGS`, вкладка настроек графа.

**Верификация (план):** SQL-проверки `graph_rag.db` (рёбра с `source_chunk` NOT NULL и отсутствующим в smk_docs якорем = 0 после первого прохода); лог-строки процесса лечения; WARNING 2839 перестаёт появляться для легаси-файлов; диагностика шаг 6 OK.

## D-2026-09-17-04 · Финальная схема фикса выгрузки БД на сервер (финализация D-2026-09-17-01) — Принято (план готов, ждёт реализации)

**Проблема:** D-2026-09-17-01; требовалась независимая проверка диагноза и финальная схема (в т.ч. поведение `shutil.copytree`).

**Решение (проверка + схема):** Диагноз подтверждён по всем пунктам, с уточнениями: (а) `shutil.copytree` АГРЕГИРУЕТ ошибки (CPython `shutil._copytree`: `except OSError → errors.append`, копирование продолжается, `shutil.Error` — один, в конце) → серверная копия после сбоя обычно полная, недокопированы только сайдкары; (б) главный риск — не гонка, а `rmtree(server_db)` ПЕРВЫМ действием: при любом сбое сервер остаётся с частичной базой, а её свежий mtime `chroma.sqlite3` реплицирует частичную базу на все гостевые станции через теневое реплицирование; (в) `clear_system_cache()` соединений паука не закрывает (прямая ссылка на клиент в `self._graph_chroma_client`), причём соединение паука открыто почти непрерывно — межраундовый сон выполняется при открытом `conn` (закрытие в `finally` после сна). Финальная схема (этап 1 плана `docs/PLANS/2026-09-17-sync-upload-fix-and-graph-autorepair.md`, правки A1–A4): снапшот `graph_rag.db` через `sqlite3.Connection.backup` (Python 3.14.3 / SQLite 3.50.4 — доступен; копирует логическую БД со всем закоммиченным WAL, без `-wal/-shm`) на локальный SSD → `copytree` в `{server_db}.tmp_{pid}` с `ignore_patterns("graph_rag.db*")` (снапшот кладём сами) → атомарная замена двумя rename (`live → .old`, `tmp → live`, откат при сбое) вместо rmtree-в-начале → `rmtree(.old)`; исчезновение чужих `-wal/-shm` при копировании не фатально (сайдкары удаляются только после чекпоинта), иные потери — fail-safe. Плюс: флаг `_graph_round_active` в пауке + дренаж до 120 с в `_push_db_to_server`, закрытие соединения паука ДО межраундового сна.

**Затронутые функции:** новый `_push_db_to_server` (перед `sync_vector_db`), блок выгрузки в `sync_vector_db`, `_graph_spider_loop` (флаг раунда, закрытие conn до сна).

**Верификация:** чек-лист в плане (часть 5): изолированный скрипт-репро гонки; после фикса — лог «Выгрузка БД на сервер: ок», отсутствие `*.db-wal/-shm` на сервере, `integrity_check` серверной копии, отказоустойчивость при недоступном Z: (серверная база не тронута).

## D-2026-09-17-05 · Финальная схема автолечения якорей GraphRAG (финализация D-2026-09-17-02) — Принято (план готов, ждёт реализации)

**Проблема:** D-2026-09-17-02; открытые вопросы — какие поля UPDATE и как встроить лечение без параллельных писателей.

**Решение (проверка + схема):** Открытый вопрос решён: UPDATE **ОБОИХ** полей — `source_chunk` (якорь, гасит warning сразу) и `chunk_id` (центр окна «метода Б»: при живом якоре warning не даёт, но при будущем сбое якоря протухший центр вернёт warning; UPDATE по `id` строки). Подтверждена двойная природа warning (`need_ids` = якорь ЛИБО окно из `chunk_id`); GraphML-рёбра (`chunk_id` = basename схемы, regex-фильтр до batch-get) warning не порождают и не лечатся — пропускать. Найдена третья причина протухания: смена алгоритма чанкования между версиями сдвигает все id без смены mtime → self-heal синка не срабатывает. Схема (этап 2 плана `docs/PLANS/2026-09-17-sync-upload-fix-and-graph-autorepair.md`, правки B1–B5): `_graph_autorepair_stale_edges(conn, docs_coll, all_id_set, window_size, max_files)` вызывается ТОЛЬКО из главного потока раунда паука (сериализованный писатель, парковка при `_db_syncing` бесплатна), расписание — раз в N раундов (`round_counter`, первый проход на первом раунде). Уровень 1 (0 токенов): детекция по семантике warning; текущие чанки файла — префиксным фильтром по `all_id_set` (надёжнее `where={"file_path"}`, не зависит от метаданных легаси); пере-якорение `_match_triplet_to_chunk` без LLM. Уровень 2 (файл, где матч не сошёлся, или файла нет в индексе): DELETE всех рёбер файла (по явным `id`) + сброс `processed_chunks` → штатное пере-извлечение FIFO/poison-guard; лимиты `graph_rag_autorepair_max_files` (≤K файлов/проход) и `graph_rag_autorepair_every` (частота) + существующий 429-бэкофф. Настройки: `DEFAULT_SETTINGS` + вкладка графа + обработчик сохранения.

**Затронутые функции:** новый `_graph_autorepair_stale_edges` (после `_rebuild_window_chunk_ids`), `_graph_spider_loop` (счётчик раундов, вызов, пересчёт `processed`), `DEFAULT_SETTINGS`, UI-вкладка графа, обработчик сохранения настроек. `_ground_graph_rows` НЕ трогается (лечение не в query-пути).

**Верификация:** чек-лист в плане (часть 5): воспроизведение warning запросом по сущности из легаси-файла → логи «Автолечение: ... — пере-якорено рёбер: N» / «сброс на пере-извлечение» → повторный запрос без warning; SQL-контроль доли рёбер с невалидными ссылками → к 0; рост «Раунд паука: кандидатов» после Уровня 2.

## D-2026-09-18-01 · Цикл автолечения («сброс → пере-извлечение → снова сброс») — Реализовано

**Статус:** Реализовано (2026-09-18). Фикс — инженер, внедрение согласовано с пользователем (выбор «Оба фикса»).

**Проблема (подтверждена продакшен-логами 2026-09-17/18, ночь в автолечении):**
Файлы V_2.4_ПК_СМК.034.20_Политика и цели в области качества.pdf (25 чанков) и Положение о закупках.pdf (~50 чанков) зациклились: автолечение каждый проход помечало их «якорь не восстановлен → сброс на пере-извлечение», паук успешно пере-извлекал файл, через 10 раундов процесс повторялся. Сотни лишних LLM-вызовов, прогресс «.Graph: N%» не растёт. Poison-guard не спасает (раунды успешны, `неудач=0`).
**Корневая причина:** `_rebuild_window_chunk_ids` возвращает окно фиксированной длины `idx..idx+window_size-1` БЕЗ учёта конца файла. У последних окон файла window_id включают фантомные id за концом файла; условие протухания в `_graph_autorepair_stale_edges` («NULL source_chunk и отсутствующий id окна») вечно ловит такие рёбра; Level-1 матчинг по части промахов триплетов не сходится → `miss=True` → принудительный сброс всего файла → цикл.

**Решение (2 фикса в `_graph_autorepair_stale_edges`, хирургические правки):**
1. Подрезка фантомного окна: при протухании NULL-ребра отсутствующими считаются только id с индексом ≤ максимального существующего индекса файла (кэш `_file_max_index` по префиксу из all_id_set). Фантомный хвост окна за концом файла больше не является признаком протухания.
2. Счётчик повторных сбросов `_autorepair_lvl2_counts` (модульный dict): если файлу уже сделано 2 сброса и якорь всё равно не восстанавливается — сброс блокируется, удаляются ТОЛЬКО протухшие рёбра (валидные рёбра и processed_chunks не трогаются). При успешном Level-1 пере-якорении счётчик файла сбрасывается.

**Затронутые функции:** `_graph_autorepair_stale_edges` (std: подрезка окна + счётчик), модульный `_autorepair_lvl2_counts`. План 2026-09-17 (v1.2) не запрещал правку B2; прочие стадии плана не затронуты.

**Верификация:** `python -m py_compile main.py` — OK; ревизия кода: уровни лог, отступы, парность скобок проверены чтением (диапазон ~2913–3032). Продакшен-проверка: после ночного отключения автолечения включить и за час убедиться, что				
				
				«сброс» для этих файлов встречается не чаще 2 раз, далее — либо «пере-якорено рёбер», либо «повторный сброс заблокирован — удалены только протухшие рёбра», прогресс Graph продолжает расти.

Идея пользователя «отключить лимит + кнопка Стоп (по образцу Hermes)» отклонена как неполная: (а) зацикливание незаметно снаружи (повтор запроса с чуть изменённой формулировкой) — безлимитный забег молотит платные запросы OpenRouter без присмотра; (б) кнопка требует человека у экрана и не чинит главный сценарий боли — обрыв без ответа при исчерпании лимита, пока пользователь отвлёкся. Отдельно: счётчик шагов — грубая прокси-защита от циклов; «второй метод» (несколько tool-вызовов за один шаг) уже поддержан кодом (~9392–9441), но модель им не всегда пользуется.

(Б) **подсказка бюджета** за 2 шага до конца («сгруппируй проверки, готовься выдать ответ»). (В) **детектор циклов — точная защита вместо грубой**: идентичный вызов (tool + json.dumps(args, sort_keys)) 2-й раз → советующее предупреждение, 3-й → принудительная финализация. (Д) **промпт-поощрение группировки** независимых вызовов в один шаг (параллельные tool_calls). Инжекция служебных сообщений (подсказка/предупреждение/директива) — role "user" с маркером `[СИСТЕМНОЕ УКАЗАНИЕ]` (не все провайдеры допускают system в середине диалога).
