## 2. Идеи на рассмотрение (без решения)
- RAG-индексация .xls (выявлено 2026-09-27 при реализации D-2026-09-25-01): сейчас `.xls` в RAG НЕ индексируются вовсе — `_read_file_content_by_path` (~2885) вызывает `extract_text_from_excel_for_rag` БЕЗ COM-конверсии, openpyxl `.xls` не читает → «Ошибка парсинга Excel» → файл пропускается и ретраится каждый синк (записей `.xls` в file_states не бывает — failed_paths вычищаются). Ветка чанкования синка `.xls` явно ожидает — намерение было, путь сломан. Кандидат: конверсия через `_get_or_convert_xls` в RAG-пути (кэш `.cache/converted_xls` уже есть); цена — зависимость синка от Excel COM. Замечание: `_get_or_convert_xls` сохраняет скрытые листы — фильтр в парсере (v2.1.2) закрывает и кэш-конверсии.
- «Версия парсера» в file_states (связана с D-2026-09-24-01/02; идея 2026-09-27): вместо одноразовых скриптов пересинка (прецедент: scripts/reset_excel_file_states.py по D-2026-09-25-01) — хранить в file_states.json версию парсера и авто-переиндексировать файлы при её смене. Цена: меняет формат ОБЩЕГО file_states.json и поведение синка — требует аккуратного плана; выгодна при будущих правках чанкера/парсеров (D-2026-09-24-02: смена чанкера требует ручного сброса file_states).
- Устойчивость синка/индексации к прерыванию (D-2026-09-24-01): инцидент 2026-09-24 — скан-PDF «завис» на постраничном Vision OCR (таймаут Vision не задан → дефолт openai-SDK 600 с + ретрай = до ~20 мин тишины на зависшую страницу), процесс убили → потерялись постраничный vision-кэш и file_states.json (пишутся только в конце прохода) → перезапуск пере-эмбеддит обработанную часть (дублирования в Chroma нет — upsert с id `{file_path}_chunk_{j}`, ~3468; цена — токены/время). Дополнительное evidence 2026-09-24: после ~30 мин тишины в логе пошёл следующий запрос (сцена «600 с timeout ×2 → страница в failed_pages → следующая страница»), а смена vision_model с nex-agi/nex-n2.5-pro:free на dots-studio/dots-3-note-preview:free сняла симптом — файл прошёл сразу: корневая причина латентности — сама free-модель (медленная генерация/очередь), таймаут — защита от любого медленного провайдера. Кандидаты правок (требуют проверки и плана от архитектора): (1) `timeout=120` в `_create_request` в `call_vision_api` (сейчас вызов без таймаута); (2) постраничный прогресс-лог в PDF-цикле `extract_smart_vision_and_pdf` (~1317–1338); (3) постраничная запись vision-кэша после каждой успешной страницы (`_parse_vision_page_markers` уже читает такой формат) вместо коммита в конце (~1351, ~1365); (4) инкрементальное сохранение file_states.json в `sync_vector_db` после каждого файла (паттерн `_cleanup_poisoned_vision_cache` ~3176) вместо `save_file_states` в конце (~3494). Эксплуатационные правила без кода: до ~20 мин тишины на Vision-странице — не убивать процесс; убийство посреди прохода = повторный эмбеддинг обработанной части; vision_model — единая настройка для PDF-страниц, картинок XWiki и OCR в чате — выбирать с учётом латентности (free-модели могут квевилиться в очереди).

- Переиспользование одного Excel-инстанса при пакетном прикреплении N файлов .xls (v3; сейчас — N последовательных запусков, как у Word в `safe_read_old_word_file`)
- GC кэша `.cache/converted_xls` (v3; файлы ~размер оригинала, в v1 не чистятся)
- Защита от «пустого» vision-кэша (v2; D-2026-09-21-01): пустой ответ модели для картинки пишется в кэш как «легитимный успех» (`--- РАСПОЗНАНО ИЗ <файл> ---` + пустота), а xwiki_sync-кэш доверяется вслепую — мимо проходят и fast-path самолечения (ловит только отсутствие кэша), и poison-cleaner (ловит только `[Ошибка Vision API`). Симптом: пустое распознавание картинки из XWiki. Ручное лечение: удалить `.cache/<имя>_<hash6>_vision.md` (искать по префиксу имени) → синк XWiki доОCR-ит картинку сам. Реализовать, ЕСЛИ сбой окажется системным (пользователь исправляет вручную); открытый вопрос дизайна — не зациклить доОCR по-настоящему пустых картинок (ретрай + различение «пустая картинка» vs «пустой ответ на содержательную», напр. проверка сложности через fitz pixmap)
- Vision-распознавание картинок, встроенных в docx (v1; D-2026-09-23-01): сейчас картинки из docx полностью теряются — `read_docx_with_indices` берёт только `p.text`, `extract_smart_vision_and_pdf` маршрутизируется только для `.pdf/.png/.jpg/.jpeg`, standalone-картинки XWiki распознаются, а тот же контент в docx на диске — нет (схемы/блок-схемы СМК-документов невидимы для RAG). Идея реализации: в docx-ветках `_read_file_content_by_path` и `load_files_bg` распаковать `word/media/*` через zipfile (в стеке), сохранить во временную папку `.cache/docx_media/` и прогнать каждую через готовый `extract_smart_vision_and_pdf` (mtime-кэш + circuit breaker достаются бесплатно), вставив OCR-текст в поток по образцу XWiki-блоков `> [!MEDIA] Иллюстрация из файла …`; привязка к абзацу — по якорям `r:embed` в `document.xml` (опционально, v2). Риски: N картинок = N Vision-вызовов (учитывать circuit breaker и 429; рассмотреть лимит/ленивое распознавание), индексация синком получит OCR-текст автоматически через `read_local_file`.
- Качество чанкования/эмбеддингов (НЕ первоочередная; D-2026-09-24-02): текущие параметры — `chunk_text` 350 симв. / перекрытие 50 (посимвольная нарезка, рвёт предложения; ~2890), Excel-строки построчно без контекста колонок (~3455), батч 100 (`chroma_batch_size`, ~5185). Контраргумент против роста чанка (D-2026-09-24-02, обсуждение 2026-09-24): один вектор = усреднение всех смыслов чанка — крупный чанк разбавляет эмбеддинг и проседает ТОЧНОСТЬ recall (нужный пункт тонет в соседях, реранку нечего ранжировать — худший тихий сценарий); эмпирический sweet spot для векторного recall 128–512 токенов, а 350 симв. русского текста ≈ 100–150 токенов — нижняя граница коридора, не «слишком мелко». Малый чанк силён в recall, крупный — в контексте модели (top_n=5 → ≤1750 симв. сейчас vs до ~6000 при 1200). Отсюда приоритеты: безопасны и не имеют риска разбавления кандидаты (2) заголовок файла/страницы и (3) Excel-префикс — они повышают различимость, не увеличивая плотность смыслов; кандидат (1) предложный чанкер — двойственный: делать с умеренной целью ~500–700 симв. (лечим посимвольную резку, почти не увеличивая разбавление), а не 800–1200; дорогая альтернатива «точность малого + контекст большого» — parent-child/sentence-window retrieval (маленький чанк ищем, большой отдаём модели) — заметно сложнее (отдельное хранение родителей/расширение окон при выдаче). Вывод: текущие 350/50 не «сломаны» — смещены в пользу точности recall; выигрыш любой правки ТОЛЬКО ПРЕДПОЛОЖИТЕЛЬНЫЙ, требует A/B-проверки на контрольных вопросах. Кандидаты: (1) предложный чанкер ~500–700 симв. (умеренная цель), (2) контекстный заголовок в каждом чанке (имя файла + № страницы — страница уже в тексте после `--- Страница N (Vision OCR) ---`), (3) префикс «Файл / Лист: X —» для каждого Excel-строчного чанка (сейчас имена колонок остаются только в первых чанках листа). Батч 100 НЕ менять (консервативно безопасен по лимитам; подъём даёт ~20% ускорения синка ценой риска 429/лимита контекста запроса). Операционный нюанс: смена чанкера НЕ триггерит переиндексацию сама (решение по mtime ~3400) — нужен ручной сброс `file_states.json` + полный пересинк (upsert перезапишет чанки по тем же id, дублей нет; стоимость — эмбеддинги всего корпуса).
