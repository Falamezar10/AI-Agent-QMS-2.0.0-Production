Симптом: пустое распознавание картинки из XWiki. Ручное лечение: удалить `.cache/<имя>_<hash6>_vision.md` (искать по префиксу имени) → синк XWiki доОCR-ит картинку сам. - Vision-распознавание картинок, встроенных в docx (v1; D-2026-09-23-01): сейчас картинки из docx полностью теряются — `read_docx_with_indices` берёт только `p.text`, `extract_smart_vision_and_pdf` маршрутизируется только для `.pdf/.png/.jpg/.jpeg`, standalone-картинки XWiki распознаются, а тот же контент в docx на диске — нет (схемы/блок-схемы СМК-документов невидимы для RAG). Идея реализации: в docx-ветках `_read_file_content_by_path` и `load_files_bg` распаковать `word/media/*` через zipfile (в стеке), сохранить во временную папку `.cache/docx_media/` и прогнать каждую через готовый `extract_smart_vision_and_pdf` (mtime-кэш + circuit breaker достаются бесплатно), вставив OCR-текст в поток по образцу XWiki-блоков `> [!MEDIA] Иллюстрация из файла …`; привязка к абзацу — по якорям `r:embed` в `document.xml` (опционально, v2). Риски: N картинок = N Vision-вызовов (учитывать circuit breaker и 429; рассмотреть лимит/ленивое распознавание), индексация синком получит OCR-текст автоматически через `read_local_file`.
- Качество чанкования/эмбеддингов (НЕ первоочередная; D-2026-09-24-02): текущие параметры — `chunk_text` 350 симв. / перекрытие 50 (посимвольная нарезка, рвёт предложения; ~2890), Excel-строки построчно без контекста колонок (~3455), батч 100 (`chroma_batch_size`, ~5185). Контраргумент против роста чанка (D-2026-09-24-02, обсуждение 2026-09-24): один вектор = усреднение всех смыслов чанка — крупный чанк разбавляет эмбеддинг и проседает ТОЧНОСТЬ recall (нужный пункт тонет в соседях, реранку нечего ранжировать — худший тихий сценарий); эмпирический sweet spot для векторного recall 128–512 токенов, а 350 симв. русского текста ≈ 100–150 токенов — нижняя граница коридора, не «слишком мелко». Малый чанк силён в recall, крупный — в контексте модели (top_n=5 → ≤1750 симв. сейчас vs до ~6000 при 1200). Отсюда приоритеты: безопасны и не имеют риска разбавления кандидаты (2) заголовок файла/страницы и (3) Excel-префикс — они повышают различимость, не увеличивая плотность смыслов; кандидат (1) предложный чанкер — двойственный: делать с умеренной целью ~500–700 симв. (лечим посимвольную резку, почти не увеличивая разбавление), а не 800–1200; дорогая альтернатива «точность малого + контекст большого» — parent-child/sentence-window retrieval (маленький чанк ищем, большой отдаём модели) — заметно сложнее (отдельное хранение родителей/расширение окон при выдаче). Вывод: текущие 350/50 не «сломаны» — смещены в пользу точности recall; выигрыш любой правки ТОЛЬКО ПРЕДПОЛОЖИТЕЛЬНЫЙ, требует A/B-проверки на контрольных вопросах. Кандидаты: (1) предложный чанкер ~500–700 симв. (умеренная цель), (2) контекстный заголовок в каждом чанке (имя файла + № страницы — страница уже в тексте после `--- Страница N (Vision OCR) ---`), (3) префикс «Файл / Лист: X —» для каждого Excel-строчного чанка (сейчас имена колонок остаются только в первых чанках листа). Батч 100 НЕ менять (консервативно безопасен по лимитам; подъём даёт ~20% ускорения синка ценой риска 429/лимита контекста запроса). Операционный нюанс: смена чанкера НЕ триггерит переиндексацию сама (решение по mtime ~3400) — нужен ручной сброс `file_states.json` + полный пересинк (upsert перезапишет чанки по тем же id, дублей нет; стоимость — эмбеддинги всего корпуса).
