## 2. Идеи на рассмотрение (без решения)
- Мультивики-синка XWiki (диагноз 2026-09-28, прод-инцидент): при смешении в одном `xwiki_urls` target'ов РАЗНЫХ вики (`/wiki/poluswiki/view/…` + `/bin/view/Main/…` главной) ВСЕ страницы очереди скачивания строятся от значений `host`/`wiki_name` ПОСЛЕДНЕГО target (`sync_xwiki`: `p_url = f"{host}/wiki/{wiki_name}/view/{page_path}"`, main.py:1799; `wiki_name` из `data-xwiki-wiki`, main.py:1710) — у главной вики `data-xwiki-wiki="xwiki"`, весь poluswiki-корпус переадресуется на `wiki/xwiki/view/…` и массово 404 (прод 2026-09-28: 151×404 за синк, «Обработано 2» — только новые Main-страницы; дневные синки 2.1.3 без bin/view-целей проходили 163/163 — версия exe не при чём, код URL-формирования идентичен 2.1.3). Временный обход без правок кода: держать список target'ов однородным внутри одного синка. Дополнительно (уточнение 2026-09-28 22:xx): найден и точный источник двойки стойких 404-страниц (лечились и на 2.1.3 — в конфиге не при чём): (1) `LogistDep/Инструкции по работе в 1С: ERP/Отслеживание движений партий` — двоеточие в имени пространства `1С: ERP` ломает формирование очереди (страницу в вики трогать НЕ надо): main.py:1786 `clean_id = fullname.split(":")[-1]` делит fullname по ВСЕМ двоеточиям (а crawl_tree, main.py:1758, делит node_id корректно с maxsplit=2), от имени `LogistDep.Инструкции по работе в 1С: ERP.Отслеживание движений партий` остаётся хвост ` ERP.Отслеживание движений партий` → запрос `view/ ERP/…` → 404; страница на сервере жива и здорова, лечится только кодом; (2) `GPP/Процессы ПСТ/Работа с браком и рекламации ПСТ` — дефекта URL-формирования нет (без двоеточий), страница видна в JSTree-дереве, но /view/ отдаёт 404 — вероятно, серверная кривизна (права на просмотр / скрытый маркер / спецсимвол в имени), нужна ручная проверка браузером под той же учёткой агента. Оба документа НИКОГДА не качались (нет в кэше и states — md5-поиск пуст), ничего не потеряно: синк подхватит их сам после устранения причин.

Проработка: (А) формировать URL скачивания по идентификатору конкретного документа (node_id JSTree уже несёт формат `document:<wiki>:Space.Page`; не применять без maxsplit `split(":")[-1]` к fullname, содержащему встроенные двоеточия, — хранить пары (wiki_name, fullname) с этапа discovery вместо общего fullname-сета); (Б) per-target метаданные: не затирать `host`/`wiki_name` в цикле обхода, держать список кортежей из каждого target; (В) анализ GC-побочек: fast-path-обработанные страницы при пропуске GC не пишут states (после починки переобработаются — оценить миграцию); (Г) защита от mixed-wiki конфигурации: guard с понятным сообщением в лог; (Д) дизайн-вопрос кросс-вики паука: spider-фильтр по target_bases (main.py:1866, граница из main.py:1726) не пускает ссылки в чужую вики — ссылки poluswiki-контента на страницы главной вики (`/bin/view/Main/…`) отбрасываются, поэтому такие страницы попадают в очередь только вручную как target'ы (случай пользователя 2026-09-28: две Main-страницы как содержимое poluswiki-страниц не подхвачены). Решить: держать по-вики-изолированный рестрикт (ожидаемо) или разрешать кросс-вики переход по явному белому списку вики; плюс per-target t_base вместо общего (тот же дефект затирания); (Е) ограничение глубины сканирования (идея 2026-09-28, прод-наблюдение): spider копает глубоко и непредсказуемо — страницы XWiki кросс-ссылаются между разделами, одна пропущенная/компромиссная ссылка тянет в очередь чужие поддеревья вплоть до «перекачать всю вики» (случай depdep: страницы файла depdep/… попали в корпус через cross-ссылки, хотя ни один target их не покрывал); риск засорения СМК-контента нерелевантными разделами. Проработать варианты: depth-лимит spider-догрузки (настройка, деф. 0–1 шаг от discovery-дерева), без-лимит JSTree discovery остаётся основной веткой; отдельный счётчик/предпросмотр «сколько страниц войдёт в очередь» до запуска; warning в лог при скачке N% выше известного объёма (связано с GC-guard); ручной stop-флаг очереди. Контраргумент против роста чанка (D-2026-09-24-02, обсуждение 2026-09-24): один вектор = усреднение всех смыслов чанка — крупный чанк разбавляет эмбеддинг и проседает ТОЧНОСТЬ recall (нужный пункт тонет в соседях, реранку нечего ранжировать — худший тихий сценарий); эмпирический sweet spot для векторного recall 128–512 токенов, а 350 симв. русского текста ≈ 100–150 токенов — нижняя граница коридора, не «слишком мелко». Малый чанк силён в recall, крупный — в контексте модели (top_n=5 → ≤1750 симв. сейчас vs до ~6000 при 1200). Отсюда приоритеты: безопасны и не имеют риска разбавления кандидаты (2) заголовок файла/страницы и (3) Excel-префикс — они повышают различимость, не увеличивая плотность смыслов; кандидат (1) предложный чанкер — двойственный: делать с умеренной целью ~500–700 симв. (лечим посимвольную резку, почти не увеличивая разбавление), а не 800–1200; дорогая альтернатива «точность малого + контекст большого» — parent-child/sentence-window retrieval (маленький чанк ищем, большой отдаём модели) — заметно сложнее (отдельное хранение родителей/расширение окон при выдаче). Вывод: текущие 350/50 не «сломаны» — смещены в пользу точности recall; выигрыш любой правки ТОЛЬКО ПРЕДПОЛОЖИТЕЛЬНЫЙ, требует A/B-проверки на контрольных вопросах. Кандидаты: (1) предложный чанкер ~500–700 симв. (умеренная цель), (2) контекстный заголовок в каждом чанке (имя файла + № страницы — страница уже в тексте после `--- Страница N (Vision OCR) ---`), (3) префикс «Файл / Лист: X —» для каждого Excel-строчного чанка (сейчас имена колонок остаются только в первых чанках листа). Батч 100 НЕ менять (консервативно безопасен по лимитам; подъём даёт ~20% ускорения синка ценой риска 429/лимита контекста запроса). Операционный нюанс: смена чанкера НЕ триггерит переиндексацию сама (решение по mtime ~3400) — нужен ручной сброс `file_states.json` + полный пересинк (upsert перезапишет чанки по тем же id, дублей нет; стоимость — эмбеддинги всего корпуса).
